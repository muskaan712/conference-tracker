# Manual verification checklist

This file lists everything in the seed dataset that a human should check
before trusting it, and every placeholder that needs a real value before
deployment. It was written by hand alongside the initial seed (not
generated by the automation pipeline — that pipeline produces its own
per-run reports under `reports/`, uploaded as CI artifacts).

Generated: 2026-07-27, updated 2026-07-28 (data-expansion pass). Re-derive
this list whenever the seed data changes meaningfully; it is a snapshot,
not a live view.

## How the seed data was produced

Of the 37 tracked conference series (25 original + 12 added in the
2026-07-28 expansion pass), **21** have at least one date verified this
session against the conference's own official website (or, for one series,
its OpenReview venue group metadata) via live web fetch, and **11** have a
tier sourced from the ICORE/CORE rankings portal. Every other field — for
all 37 series — is either omitted or explicitly marked `unverified` /
`Unclassified` / `Location not announced` rather than guessed. Nothing in
this dataset was invented; where a session verification wasn't possible,
the record is intentionally sparse.

## Rankings

Tiers were only assigned where the ICORE/CORE portal search this session
explicitly listed the venue as A*. That means several venues most
researchers would consider clearly A or B (e.g. NAACL, COLING, SIGIR,
WSDM, CIKM, ECML PKDD, UAI, MLSys) are shown as **Unclassified** here
simply because a per-venue lookup wasn't performed this session — not
because they lack a real ranking. Before publishing, do the remaining
CORE lookups at <https://portal.core.edu.au/conf-ranks/> and fill in
`ranking.source` / `ranking.sourceUrl` / `ranking.verifiedAt` for each.

## Discovery sources needing a real parser

`src/data/discovery-sources.json` has an entry for the CORE rankings portal
with `parser: "core-rankings-search"`, but no adapter with that ID exists
yet in `scripts/shared/adapters.ts` — it currently falls back to the
manual-review adapter and contributes nothing automatically. The generic
`official-site-generic` (JSON-LD) adapter is wired up for the 9 originally
verified official sites, but most conference sites don't publish schema.org
`Event` JSON-LD, so it will frequently return zero candidates even when it
runs successfully. This is an expected, honest gap — see the README's
"Known limitations" section.

As of the 2026-07-28 pass, two new adapters exist and were live-tested:

- **`ai-deadlines-yaml`** (`scripts/shared/ai-deadlines-adapter.ts`), reading
  the MIT-licensed `paperswithcode/ai-deadlines` community YAML feed —
  `npm run check-sources` confirmed the feed URL is reachable. This adapter
  covers many series in one source, matched via
  `scripts/shared/series-aliases.ts`; it was not run end-to-end against the
  live feed's actual current content in this session (only unit-tested
  against fixtures) — a human should run `npm run discover` once to see its
  real output before enabling it unattended in the weekly workflow long-term.
- **`openreview-venue-group`** (`scripts/shared/openreview-adapter.ts`),
  reading an OpenReview venue's public group metadata — confirmed working
  against the live `api2.openreview.net` for `ICLR.cc/2026/Conference` and
  `IEEE.org/DSAA/2026/Conference` during this session's research (used to
  source the DSAA 2026 submission deadline above), but no
  `discovery-sources.json` entry uses this parser yet — a human needs to add
  one per OpenReview-hosted venue they want scanned automatically.

The `important-dates-table` adapter also now falls back to a third layout
(a plain "label: date" bulleted list, via `parseStructuredLists`) in
addition to tables and definition lists — see
`scripts/shared/parse-helpers.ts`.

## AoE deadline time-of-day audit (2026-07-28)

Every `isAoE: true` date in `src/data/conferences/*.json` was scanned for the
"midnight instead of 23:59" bug — AoE deadlines are, by academic convention,
end-of-day (23:59 AoE), not start-of-day, and `T00:00:00` on an AoE-flagged
submission deadline almost always means "written at the wrong time," not
"genuinely due at midnight."

**Fixed** (verified against the official CFP/programme page before changing;
only the time-of-day changed, never the calendar date):

- AAAI 2027 — abstract, full-paper, and supplementary/code deadlines
  (`T00:00:00` → `T23:59:00`), confirmed against
  `aaai.org/conference/aaai/aaai-27/main-technical-track-call/` ("11:59 PM
  UTC-12").
- NeurIPS 2026 — abstract and full-paper deadlines, confirmed against
  `neurips.cc/Conferences/2026/CallForPapers` ("AOE").
- EMNLP 2026 — ARR submission deadline and Industry Track deadline, confirmed
  against `2026.emnlp.org` and `2026.emnlp.org/calls/industry_track/`
  ("11:59 PM UTC-12:00, AoE").
- EACL 2027 — ARR submission deadline (same convention as the other
  ACL Rolling Review-linked deadlines above; the general ARR dates page
  itself does not state a time, so this follows the family-wide AoE
  convention already recorded on the record, not an independently
  re-verified EACL-specific source).

**Deliberately left unchanged** (do not blindly "fix" these — see below):

- `emnlp-2026-author-response-start` — this is the *start* of a window
  (`endsAt` already correctly reads `23:59:00`); a window opening at
  midnight AoE is correct, not a bug.
- `emnlp-2026-notification`, `emnlp-2026-camera-ready`,
  `neurips-2026-notification` — these are announcement/due dates, not
  submission deadlines, and it's genuinely ambiguous whether the official
  page's "AoE" framing applies to them the same way. **Flagged for human
  re-verification**, not changed.
- While checking EMNLP 2026, one fetch of `2026.emnlp.org` returned
  "Camera-ready papers due: August 30, 2026" — different from the
  `2026-09-20` currently on file. This is a single automated fetch/summary,
  not a confirmed source discrepancy — **a human should check the live page
  directly** before trusting either date.

A display bug was also found and fixed while verifying this: `formatOriginal`
and `accessibleDeadlinePhrase` in `src/lib/datetime.ts` used to reproject an
AoE deadline's resolved UTC instant back into a calendar date, which silently
shifted the *displayed* date forward by one day for any AoE time past 12:00
(exactly the common 23:59 AoE case) — e.g. "28 July 2026, 23:59 AoE" was
rendering as "29 July 2026." Fixed to read the authored wall-clock
date/time directly instead. See `tests/unit/datetime.test.ts` for the
regression tests.

## Other things a human should double-check

- The `.github/workflows/weekly-conference-update.yml` workflow assumes the
  repository's Actions have "Read and write permissions" enabled (Settings →
  Actions → General → Workflow permissions), in addition to the explicit
  `permissions:` block already in the workflow file.
- No `automated-update` / `conference-data` / `needs-verification` labels
  exist in a fresh repo by default — create them once (`gh label create ...`)
  or the label-attach step in the weekly workflow will no-op silently.
- `check-source-health.ts` was run once during development against the real
  internet; all 11 sources responded successfully as of 2026-07-27. Re-run
  it periodically — it does not run automatically outside the weekly workflow.
