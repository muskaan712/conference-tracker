# Manual verification checklist

This file lists everything in the seed dataset that a human should check
before trusting it, and every placeholder that needs a real value before
deployment. It was written by hand alongside the initial seed (not
generated by the automation pipeline — that pipeline produces its own
per-run reports under `reports/`, uploaded as CI artifacts).

Generated: 2026-07-27. Re-derive this list whenever the seed data changes
meaningfully; it is a snapshot, not a live view.

## How the seed data was produced

Of the 25 tracked conference series, **9** have at least one date verified
this session against the conference's own official website (via live web
fetch), and **11** have a tier sourced from the ICORE/CORE rankings portal.
Every other field — for all 25 series — is either omitted or explicitly
marked `unverified` / `Unclassified` / `Location not announced` rather than
guessed. Nothing in this dataset was invented; where a session verification
wasn't possible, the record is intentionally sparse.

## Rankings

Tiers were only assigned where the ICORE/CORE portal search this session
explicitly listed the venue as A*. That means several venues most
researchers would consider clearly A or B (e.g. NAACL, COLING, SIGIR,
WSDM, CIKM, ECML PKDD, UAI, MLSys) are shown as **Unclassified** here
simply because a per-venue lookup wasn't performed this session — not
because they lack a real ranking. Before publishing, do the remaining
CORE lookups at <https://portal.core.edu.au/conf-ranks/> and fill in
`ranking.source` / `ranking.sourceUrl` / `ranking.verifiedAt` for each.

## Discovery sources needing a real parser

`src/data/discovery-sources.json` has an entry for the CORE rankings portal
with `parser: "core-rankings-search"`, but no adapter with that ID exists
yet in `scripts/shared/adapters.ts` — it currently falls back to the
manual-review adapter and contributes nothing automatically. The generic
`official-site-generic` (JSON-LD) adapter is wired up for the 9 verified
official sites, but most conference sites don't publish schema.org `Event`
JSON-LD, so it will frequently return zero candidates even when it runs
successfully (confirmed: it returned 0 candidates against all 9 sources in
a live test run this session). Both are expected, honest gaps — see the
README's "Known limitations" section.

## Branding status

All public placeholders have been replaced. Site branding lives in
`src/lib/site-config.ts` (`siteConfig`):

- `ownerName`: "Muskaan Chopra"
- `title` / `description`: set to the real site title and description
- `githubUrl`, `personalWebsiteUrl`, `contactEmail`: **intentionally unset**
  — these have no real value yet. Every UI element that would show one
  (footer links, the About page) checks truthiness and hides itself rather
  than rendering a dead link, `#`, or "coming soon". Fill them in directly
  in `site-config.ts` once real values exist.
- `NEXT_PUBLIC_SITE_URL` — optional. `getSiteUrl()` in `src/lib/site-url.ts`
  falls back to Vercel's own `VERCEL_PROJECT_PRODUCTION_URL` / `VERCEL_URL`
  env vars automatically, then to `http://localhost:3000` for local dev. Set
  this explicitly only once you've pinned a custom production domain.

## Associated events (workshops, tutorials, shared tasks, competitions)

The events architecture (schema, validation, routes, timeline/planner/paper
integration, discovery pipeline) is fully built — see
[`docs/EVENTS.md`](docs/EVENTS.md). **`src/data/events/` intentionally
contains no event data yet.** Populating even a small starter set honestly
requires visiting each event's current official page to confirm its name,
type, and status; that verification pass was not performed as part of this
change, specifically to avoid inventing a plausible-sounding workshop name,
deadline, or ranking. Running `npm run discover-events` /
`npm run update-events` against the discovery-sources registry is the
intended way to populate this directory once at least one
`workshop-programme`-type source is configured and enabled — none is
configured in the registry yet either, for the same reason.

## Other things a human should double-check

- The `.github/workflows/weekly-conference-update.yml` workflow assumes the
  repository's Actions have "Read and write permissions" enabled (Settings →
  Actions → General → Workflow permissions), in addition to the explicit
  `permissions:` block already in the workflow file.
- No `automated-update` / `conference-data` / `needs-verification` labels
  exist in a fresh repo by default — create them once (`gh label create ...`)
  or the label-attach step in the weekly workflow will no-op silently.
- `check-source-health.ts` was run once during development against the real
  internet; all 11 sources responded successfully as of 2026-07-27. Re-run
  it periodically — it does not run automatically outside the weekly workflow.
